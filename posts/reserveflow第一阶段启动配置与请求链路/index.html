ReserveFlow 是基于 slabiak/AppointmentScheduler 改造的 Java 后端学习项目，保留上游 Git 历史与 MIT 许可证

一、请求如何进入数据库#

业务请求的基本路径：

HTTP 请求 → 安全过滤器链 → Controller → Service → Repository → 数据库
层次 职责
安全过滤器链 在 Controller 之前处理认证、访问权限检查
Controller 接收路径参数、查询参数、请求头和请求体，调用业务服务
Service 执行业务校验、组织查询或写入，并定义事务边界
Repository 提供数据库访问方法
DTO / View 表达接口输入、输出，避免直接返回完整数据库实体

Spring Data JPA 提供 Repository 的运行时实现。例如 findAllByActiveTrueOrderByName() 表示查询启用的资源并按名称排序，不需要手写同名方法的实现。

JPA 是持久化规范，Hibernate 是其实现之一，负责实体与数据表的映射及底层持久化操作。@Entity、@Table、@Column 描述对象与表结构的对应关系。

二、启动配置与数据库初始化#

1. YAML 与环境变量#

server:
  port: ${SERVER_PORT:8080}

完整属性名是 server.port。${变量名:默认值} 表示读取对应变量，未提供时使用默认值。把 8080 改为 8081 只会改变默认值；若环境变量已指定端口，仍以该变量为准。

框架配置如 spring.* 由对应框架读取；app.* 是本项目定义的属性，由业务代码通过 @Value 等方式读取。

2. 基础配置与 local 覆盖#

激活 local 后，Spring Boot 同时读取 application.yml 和 application-local.yml。后者覆盖同名属性，未覆盖的配置继续沿用基础文件；命令行参数等更高优先级配置仍可能覆盖它们。

配置 基础配置 local 配置
数据库 PostgreSQL H2 内存数据库，PostgreSQL 兼容模式
缓存实现 Redis simple，进程内缓存
Redis 自动配置 默认启用 排除指定的 Redis 自动配置
演示数据 默认启用 明确启用
业务邮件通知 默认关闭 明确关闭
Hibernate 表结构检查 validate 沿用 validate
JWT 有效期 2h 沿用 2h

local 仅用于开发，不代表真实 PostgreSQL、Redis 环境。H2 数据保存在当前应用进程内，重启进程后不会保留原来的预约数据。

4. Flyway、Hibernate 与演示数据#

数据库初始化的依赖顺序：

加载配置并建立数据库连接
  → Flyway 执行尚未应用的迁移脚本
  → Hibernate validate 校验实体与表结构
  → DemoDataInitializer 在启动阶段写入演示数据
  • Flyway：管理数据库结构版本，执行 db/migration/V1__create_reservation_schema.sql 等迁移，并记录已执行版本，不会每次启动都重复建表。
  • Hibernate validate：校验已有表结构；缺表或结构不匹配会导致启动失败。
  • DemoDataInitializer：创建演示用户、资源和开放时间，不负责建表；用户密码经 BCrypt 哈希后保存。

全新的 H2 数据库关闭演示初始化后，表仍可正常建立、应用仍可启动，但默认演示账号不存在，无法登录。关闭初始化不会删除持久化数据库中已经存在的数据。

三、登录认证与 JWT 签发#

POST /api/auth/login
  → AuthController.login()
  → AuthenticationService.login()
  → AuthenticationManager.authenticate() 校验凭证和账号状态
  → 查询业务实体 UserAccount
  → TokenService.issue() 签发 JWT

查询到用户只代表账号存在，不代表密码正确。authenticate() 成功时返回认证结果，失败时抛出异常；当前业务代码即使没有接收返回值，也通过异常阻止错误密码获得 JWT，并返回 401。

AuthenticationManager 是接口，Spring 注入运行时实现。用户名密码认证的典型路径是 ProviderManager → DaoAuthenticationProvider → UserDetailsService，通过 PasswordEncoder.matches(明文密码, 数据库哈希) 校验密码，不是解密密码或直接比较哈希字符串。

登录时构造的 UsernamePasswordAuthenticationToken 是 Spring Security 的凭证载体，不是返回给前端的 JWT。认证内部查询用户，业务代码随后又读取 UserAccount，因此当前流程存在重复查询。

JWT 只包含选定字段，不包含整个用户对象或密码哈希：

字段 本项目中的含义
sub 令牌所属身份，取用户邮箱；由 .subject(user.getEmail()) 设置
uid 用户 ID
roles 业务角色名称，例如 ["USER"]
iss 签发者
iat / exp 签发时间、过期时间

issue() 使用 HS256 生成带签名的 JWT。签名用于验证完整性，不是加密，不能在 JWT 中放入敏感信息。

四、JWT 校验与角色映射#

后续请求通过请求头携带令牌：

Authorization: Bearer <accessToken>

安全过滤器提取 Bearer Token
  → JwtAuthenticationProvider
  → NimbusJwtDecoder 校验签名、有效期等
  → JwtAuthenticationConverter 构建身份和权限
  → 安全上下文保存认证结果
  → 接口访问检查通过后进入 Controller

GET /api/bookings/me 不带令牌时返回 401；有效令牌通过检查后，Controller 的 Principal 表示当前身份，principal.getName() 默认对应 JWT 的 sub，即用户邮箱。身份已认证但权限不足时返回 403。

USER 与 ROLE_USER 属于不同表示层，不会相互改写：

位置 表示
UserAccount.role 枚举 USER
登录时构建的 UserDetails .roles("USER") 生成权限 ROLE_USER
JWT 的 roles ["USER"]
JWT 转换后的认证对象 转换器添加 ROLE_ 前缀，得到 ROLE_USER

认证判断“身份是否可信”，授权判断“能否执行操作”。本项目登录和资源 GET 接口允许匿名访问，/api/admin/** 要求 MANAGER 或 ADMIN，其余业务接口要求已认证。

五、资源查询与可用时段计算#

资源列表链路：

GET /api/resources
  → ResourceController.list()
  → ResourceService.listActive()
  → findAllByActiveTrueOrderByName()
  → 转换为 ResourceView 返回

可用时段接口为 GET /api/resources/{id}/availability?date=YYYY-MM-DD，id 来自路径参数，date 来自查询参数。AvailabilityService 的计算过程：

  1. 检查资源是否存在，查询对应星期的有效开放时间；没有开放时间则返回空列表。
  2. 查询当天开放区间内已占用的时段起点。
  3. 按 30 分钟生成候选时段起点。
  4. 排除已经过去、已经被占用的起点。
  5. 将剩余起点转换为半小时的 TimeSlotView。

例如开放时间为 08:00—10:00，则有四个候选时段；若 08:30—09:00 已占用且其他时段均未过期，返回其余三个。

可用时段是基于开放时间、占用记录和当前时间计算的，不是直接读取一张“可用时段表”。@Cacheable 命中缓存时可以跳过方法体，因此同一资源、同一日期重复查询可能不命中 Service 内部断点。

六、创建预约与写库路径#

POST /api/bookings
  → JWT 认证与接口访问检查
  → BookingController.create()
  → BookingService.create()
  → 校验幂等键、用户、预约时间、资源与开放时间
  → 保存 Booking
  → 按 30 分钟拆分并保存 BookingSlot
  → flush，同步待处理修改到数据库
  → 发布预约事件并返回结果，事务正常提交

Controller 从 principal.getName() 获取用户邮箱，不由请求体自行指定预约人。新预约须在未来、不能跨天、起止时间对齐半小时边界，时长为半小时至四小时，并在资源开放时间内。

一次 08:00—09:00 的预约对应：

表 记录 用途
bookings 1 条预约 保存用户、资源、完整时间区间和状态
booking_slots 2 条占用，起点为 08:00、08:30 保存具体半小时时段，通过 booking_id 关联预约

save() 不保证立即执行 INSERT；flush() 会同步待处理修改，但不等于提交事务。BookingService.create() 的 @Transactional 将预约和全部时段写入放在同一事务中。

正常创建返回 201 Created，状态为 CONFIRMED。随后通过 GET /api/bookings/me 查看预约，再查询可用时段，确认已预约的半小时区间不再出现。

七、幂等键的基本认识#

幂等键与预约 ID 不同：客户端在一次新操作发送前生成 Idempotency-Key，后端创建预约时生成 Booking.id。UUID 只是生成编号的一种方式，幂等键并不强制使用 UUID。

  • 同一用户以相同键、相同资源和时间区间重试：返回原预约，不再创建。
  • 同一用户以相同键提交不同内容：返回 409。
  • 换一个新键：按新的创建操作处理，不会被当作原操作的重试。

关键规则是“新操作用新键，同一次操作重试复用原键”。当前演示前端每次提交直接生成新 UUID，尚未实现跨重试保留原键的完整流程。重复返回原预约时，当前 Controller 仍使用 201，不能仅凭状态码判断是否新增记录。

数据库中的 (user_id, idempotency_key) 和 (resource_id, slot_start) 唯一约束分别限制重复操作记录、重复时段占用。并发冲突、事务回滚与缓存一致性留到后续阶段深入。

八、断点调试方法#

IDEA 默认快捷键 用途
F8 执行当前行，通常不进入被调用方法
F7 尝试进入被调用方法
Shift+F8 执行完当前方法，返回调用者
F9 继续运行至下一个断点或请求结束

只在关键节点设置断点：Controller 接收参数、Service 业务处理、数据库写入前后。节点之间用 F9，局部观察用 F8，不需要逐行追踪完整框架源码。

蓝色执行行通常尚未执行；变量应在赋值完成后观察。Frames 显示调用栈，切换栈帧只是查看上下文，不会让程序倒退执行。跟踪 JWT 校验等更早阶段时，需要先设置断点，再重新发送请求。
