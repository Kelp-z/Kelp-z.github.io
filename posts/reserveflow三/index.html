ReserveFlow三

从两次可用时段查询的断点记录，理解 Spring 如何读写缓存、处理 Redis 异常，以及在预约事务提交后删除旧结果。

连续两次查询 1 号会议室同一天的可用时段，Controller 两次都收到了请求，Service 里的查库代码却只执行了一次。理解这次调试，要从 Controller 里的这一行开始：

return availability.availability(id, date);

一、同一个请求，为什么第二次跳过了 Service 方法体#

在 IDEA 的变量窗口里，Controller 持有的 availability 显示为 AvailabilityService$$SpringCGLIB$$0。这是 Spring 为 Service 创建的代理对象。Controller 调用它时，Spring 会先处理方法上的缓存注解：

@Cacheable(cacheNames = "availability", key = "#resourceId + ':' + #date")
@Transactional(readOnly = true)
public AvailabilityView availability(Long resourceId, LocalDate date)

cacheNames 指定缓存名，key 指定如何根据方法参数生成键。例如资源为 1、日期为 2026-11-10，得到的键就是 1:2026-11-10。同一资源换一天查询，会用到另一个键。

我用 local 配置启动项目，在 Controller 调用 Service 的那一行和 Service 方法体的第一句 resources.existsById(resourceId) 分别设置断点，连续请求同一地址：

curl.exe "http://localhost:8080/api/resources/1/availability?date=2026-11-10"
请求 Controller 断点 Service 方法体断点
第一次 停住 停住，开始查询数据库
再次查询相同资源和日期 停住 按 F9 后直接返回结果

第一次查询时，缓存里还没有这个键。Spring 继续执行 availability() 方法体：先确认资源存在，再查当天的开放时间和已占用时段，从每半小时一个的候选列表里排除已过去、已被占用的时段。方法最后返回一个 AvailabilityView。查询数据库和计算列表由 Service 完成，读取缓存、把返回值写入缓存由 Spring 代理负责。

第二次请求仍会执行 Controller 里的同一行。代理按相同的键取到了上次的返回值，直接交回 Controller，因此 Service 方法体的断点没有再次触发。

二、Redis 怎样接入，键和值从哪里来#

ReserveFlow 引入了 spring-boot-starter-data-redis，在启动类上用 @EnableCaching 开启注解缓存。默认配置把缓存类型设为 redis，连接地址默认为 localhost:6379，可通过 REDIS_HOST、REDIS_PORT 覆盖。Redis 缓存项的过期时间配置为 5 分钟。

学 Redis 命令时，执行 SET name "张三" 就写入了一个键和值，无需先声明变量。项目中的对应关系是：

内容 本次查询的例子
缓存名 availability
根据参数生成的键 1:2026-11-10
默认前缀规则下的 Redis 键 availability::1:2026-11-10
值 方法返回的 AvailabilityView，包含资源、日期、时区和可用时段列表，写入 Redis 时需要序列化

本机 Redis 当时能对 PING 返回 PONG，说明服务可以连接。上面的断点实验使用了另一套配置：application-local.yml 选择 H2 和 spring.cache.type: simple，结果保存在应用进程内，重启后就会清空。实验观察到的是 Spring 的缓存命中行为，5 分钟的过期时间属于默认 Redis 配置。

三、Handler 是谁调用的#

Handler 是处理器。在这个项目里，CacheErrorHandler 是一个 Java 接口，约定缓存操作抛出异常时可以调用哪些方法。以查询 1 号会议室为例，缓存里没有当天的记录是正常的未命中，Spring 会继续查库。只有读取操作抛出异常，才会调用 handleCacheGetError(...)。

一个对象怎样成为 Spring 使用的错误处理器#

最初的配置写了一个带 @Bean 的 cacheErrorHandler() 方法。Spring 容器因此管理了一个处理器对象，但注解缓存还有自己的配置入口：它从实现了 CachingConfigurer 的配置类取得 errorHandler()。我把 CacheConfig 接入了这个入口。下面摘出读取异常这一支：

@Configuration
public class CacheConfig implements CachingConfigurer {
    @Bean
    @Override
    public CacheErrorHandler errorHandler() {
        return new CacheErrorHandler() {
            public void handleCacheGetError(RuntimeException exception, Cache cache, Object key) {
                warn("get", exception, cache, key);
            }
            // 省略写入、删除、清空的处理方法及记录日志的 warn 方法
        };
    }
}

读这段代码时，我最容易混淆的是两个相似的方法名。外层的 errorHandler() 返回对象。new CacheErrorHandler() { ... } 创建的是匿名实现类的实例，@Bean 将这个实例交给已有的 Spring 容器管理。实现 CachingConfigurer 让缓存拦截器能取得这个实例，@Override 让编译器检查方法签名。内层的 handleCacheGetError(...) 才是对象处理读异常时执行的方法。

从 Controller 的一行调用追到 catch#

Spring Framework 6.2.11 处理这个同步查询时，主要经过以下方法：

方法 这一步做什么
CacheInterceptor.invoke() → CacheAspectSupport.execute() 代理接到 Controller 对 availability() 的调用，先检查缓存
findCachedValue() → findInCaches() 生成键，在名为 availability 的缓存中查找
AbstractCacheInvoker.doGet() 调用 cache.get(key)，捕获这次读取抛出的异常

在 doGet() 里可以直接看到谁调用了自己的处理方法：

try {
    return cache.get(key);
} catch (RuntimeException ex) {
    getErrorHandler().handleCacheGetError(ex, cache, key);
    return null;
}

getErrorHandler() 取得配置好的对象。Spring 把刚捕获的异常、正在访问的缓存和本次查询的键传给它。默认处理器会重新抛出异常，程序走不到下一行。项目的处理器只记录警告，方法正常结束，执行就回到 catch 中的 return null。这个 null 表示缓存没有给出结果，拦截器接下来调用 AvailabilityService.availability() 查数据库。查库成功后，如果回写缓存也失败，handleCachePutError(...) 记录警告，调用者仍能拿到已经算出的列表。这条故障路径按源码梳理，本次断点实验观察到的是正常的未命中和命中。

四、监听器怎样收到预约事件#

创建事件与发布事件是两次调用#

假设用户取消明天 10:00 的预约。BookingService.cancel() 在事务里执行这几行：

slots.deleteByBookingId(booking.getId());
booking.cancel();
events.publishEvent(eventFor(booking, "CANCELLED"));

前两行释放时段、修改预约状态。最后一行按 Java 的求值顺序可以拆开读：

BookingChangedEvent event = eventFor(booking, "CANCELLED");
events.publishEvent(event);

第一行调用项目自己的 eventFor(...)，创建一个普通的 BookingChangedEvent 对象。它保存资源 ID、日期、预约起止时间及 "CANCELLED" 等数据。假如程序停在两行之间，对象已经存在，Spring 还没收到这次事件。

第二行把对象交给 Spring。events 是通过构造器注入的事件发布器，变量类型是 Spring 的接口 ApplicationEventPublisher。在 IDE 里点进接口，只能看到方法约定；运行时 Java 会调用注入对象的实际实现。publishEvent(...) 返回 void，说明调用方不用接收返回值。这行代码产生的效果是发布事件。如果省掉它，单靠创建对象不会触发本次缓存删除。

Spring 怎么找到监听方法，又在何时调用它#

BookingEventListeners 标有 @Component。Spring 在启动时发现其中带监听注解的方法，负责删除缓存的是这一段：

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void evictAvailability(BookingChangedEvent event) {
    Cache cache = cacheManager.getCache("availability");
    if (cache != null) cache.evict(event.resourceId() + ":" + event.date());
}

这里的参数类型回答“接收什么”。发布的对象是 BookingChangedEvent，与方法参数匹配。即使把方法名从 evictAvailability 改成 clearCache，保留注解和参数类型，它仍然能收到同一种事件。注解里的阶段回答“什么时候执行”。沿着这笔取消操作，可以看清三个时刻：

  1. 事务内发布事件。 Spring 找到匹配的监听方法，为当前事务登记一次提交后的调用。此时旧缓存仍在。
  2. 数据库成功提交。 Spring 将事件作为参数传入 evictAvailability(event)，方法体里的 cache.evict(...) 删除该资源当天的缓存。若事务回滚，这个提交后监听方法不会运行。
  3. 下一次查询。 代理按同一个键查询，缓存未命中，Service 重新计算列表。已经释放的 10:00 时段会重新出现在结果中。

创建预约走相同的发布路径，只是调用了 eventFor(booking, "CONFIRMED")。"CONFIRMED" 和 "CANCELLED" 都是同一种事件对象的 action 字段值。创建成功会让旧列表多显示一个已占用时段，取消成功会让旧列表少显示一个已释放时段。两种情况都只需用资源 ID 和日期删除同一个键，因此可以共用监听方法。另一个接收相同事件的 notifyUser() 同样等到提交后触发，并通过 @Async 异步处理通知。

五、为什么等事务提交后再删#

假如把删缓存放在提交之前，两个请求就可能这样交错：

  1. A 正在预约 10:00，已经写入时段并删除缓存，事务尚未提交。
  2. B 此时查询，因为没有缓存而访问数据库。B 还看不见 A 未提交的占用记录，于是把“10:00 可用”重新写入缓存。
  3. A 提交成功。数据库里的 10:00 已被占用，缓存却保留着 B 刚写入的旧列表。

AFTER_COMMIT 避免了这种因提前删除而产生的时序问题，但数据库提交和缓存删除仍是两个操作。若数据库已经提交，而对应缓存删除失败，下一次查询命中旧值时会出现两种结果：

已提交的操作 旧缓存显示 数据库中的实际状态
预约 10:00 成功 10:00 仍可选 已被占用，再次预约会因时段唯一约束冲突而返回 HTTP 409
取消 10:00 成功 列表里仍看不到 10:00 时段已释放，重新查库时会出现在可用列表里

这里还有一个调用方式上的区别。查询上的 @Cacheable 经过 Spring 缓存拦截器，能调用第三节的错误处理器。监听方法里则直接执行 cache.evict(...)，这行代码不会自动经过该处理器。默认 Redis 配置的过期时间可以限制旧缓存的存留时间，写入预约时真正阻止重复占用的是数据库的 UNIQUE (resource_id, slot_start)。上述预约、取消后的缓存变化是按代码时序推演的，本次断点实际观察的是第一节的连续查询。
