一.点击reference超时问题#

1.问题描述#

​ 点击reference时会报超时错误，且reference无法正常展示

2.原因分析#

​ 造成这个问题的原因是：

​ 1.页面请求和Crossref派发耦合：

​ 用户只是打开 References 页面，后端就会同步执行待处理引用的派发逻辑，“准备任务、查缓存、更新状态、写入队列”这些步骤仍然发生在当前 HTTP 请求中，所以引用的文献越多，处理的时间越长

​ 2.后台队列扫描读取了不必要的大字段

​ 定时任务查询是：

SELECT *
FROM spm_references

​ Crossref派发只需要部分字段，而查询整张表的方式会增加数据库的查询成本

3.解决方法#

3.1 页面加载不再派发 Crossref#

现在打开 References 页面只做：

  • 查询当前解析版本；
  • 查询参考文献；
  • 查询作者和作者匹配关系；
  • 计算统计指标；
  • 组装并返回页面数据。

这样页面响应时间不会再直接受待检索引用数量影响。

3.2 Crossref 改由定时任务后台派发#

由定时任务扫描待处理引用：

@Scheduled(fixedDelay = 10000)
public void dispatchPending()

修改后每 10 秒扫描一次，每批最多处理 60 条，然后将任务放入检索队列。

因此流程变成：

用户打开 References
        |
        |-- 只查询并展示数据，快速返回
        |
后台定时任务
        |
        |-- 扫描 PENDING / PARTIAL / NOT_REQUESTED
        |-- 派发 Crossref/OpenAlex
        |-- 异步回写检索结果
        |
前端轮询
        |
        |-- 刷新最新检索状态

页面和检索任务由同步关系改成了异步关系。

3.3 后台扫描改成只查询必要字段#

提交将 Crossref 队列查询从：

SELECT *

改为：

SELECT <include refid="workspaceReferenceColumns"/>

这个字段列表不包含 retrieved_payload_json，所以后台批量扫描时不会加载大 JSON。

3.4删除重复的完整查询方法#

删除了：

selectAllByExtractionId()

以及对应的：

SELECT *
FROM spm_references
WHERE extraction_id = #{extractionId}

普通查询统一使用轻量字段列表，避免不必要地把完整检索结果加载出来。

二.参考文献状态轮询优化#

前面的修改解决了第一次打开 References 页面时的超时问题，但页面打开后仍然需要定时查询 Crossref、OpenAlex 和 Google Scholar 的检索进度。

1.问题是什么#

检索任务是异步执行的。为了及时显示最新结果，前端会每隔 5 秒刷新一次状态。

优化前，轮询调用的是完整工作区接口：

GET /submission/submission/{id}/reference

这意味着每隔 5 秒都会重新加载整个 References 工作区，包括：

  • 查询全部参考文献；
  • 查询参考文献作者和作者匹配关系；
  • 处理重复文献；
  • 计算自引、他引、年份和文献类型等指标；
  • 构造每条文献的审核状态；
  • 查询检索任务和队列状态；
  • 向前端返回完整的 References 数据。

即使检索状态没有发生任何变化，系统仍然会重复执行上述工作。

2.原因是什么#

系统把两种不同的请求使用场景混在了同一个接口中：

  1. 第一次进入页面时，需要加载完整的 References 工作区。
  2. 后续轮询时，通常只需要知道检索进度和数据是否发生变化。

轮询实际上只关心以下信息：

  • Crossref 和 OpenAlex 的检索进度；
  • 检索队列的运行状态；
  • Google Scholar 任务状态；
  • 当前解析版本是否变化；
  • Reference 数据是否有新修订。

但是旧逻辑每次都返回完整数据，造成数据库重复查询、后端重复计算、网络传输量增加以及 Vue 表格反复渲染。多人同时打开 References 页面时，这种每 5 秒一次的全量请求会持续增加测试服压力。

3.解决方法#

3.1 新增轻量状态接口#

后端新增接口：

GET /submission/submission/{id}/reference/status

该接口仍然会执行用户权限和稿件归属校验，但不会构造完整的 References 工作区。

接口只返回轮询所需的信息：

extractionId
referenceRevision
workspaceVersion
downstreamStatus
retrievalProgress
retrievalQueueHealth
googleVerifyTasks
workspaceChanged

它不会返回完整参考文献列表、作者匹配详情、自引和他引分组以及全部统计指标，因此响应体和后端计算量都更小。

3.2 使用工作区版本号判断是否需要全量刷新#

后端使用 extractionId 和 referenceRevision 组成工作区版本号：

workspaceVersion = extractionId:referenceRevision

例如：

44:8

表示当前解析版本 ID 为 44，Reference 数据修订版本为 8。

前端轮询时会把自己当前的 workspaceVersion 和 downstreamStatus 传给后端。后端将它们与当前数据库状态比较：

工作区版本不同
    或
downstreamStatus 不同

只要其中一项发生变化，后端就返回：

{
  "workspaceChanged": true
}

3.3 只有数据变化时才重新加载完整工作区#

前端改为每隔 5 秒调用轻量状态接口：

每 5 秒请求 /reference/status
        |
        |-- workspaceChanged = false
        |      只更新检索进度、队列状态和 Google 任务状态
        |
        |-- workspaceChanged = true
               再请求一次完整的 /reference 工作区

三.优化后的完整流程#

第一次打开 References
        |
        |-- 请求完整 /reference 接口
        |-- 加载参考文献、作者、统计指标等页面数据
        |
后台检索进行中
        |
        |-- 前端每 5 秒请求轻量 /reference/status 接口
        |
        |-- 状态未变化：只更新进度信息
        |
        |-- 状态发生变化：重新加载一次完整工作区

第一次优化解决的是“打开页面时同步派发 Crossref 导致超时”；第二次优化解决的是“页面打开后频繁全量轮询造成持续性能压力”。两次优化组合后，页面加载、后台检索和状态刷新三条链路彼此分离。
