ReserveFlow 二

理解 ReserveFlow 中预约事务、数据库唯一约束、并发冲突与接口幂等。

一、一次预约为什么要拆成多个时段#

项目按 30 分钟粒度保存预约占用。用户预约 10:00—11:30 时，完整预约保存到 bookings 表，同时生成三个 booking_slots：

10:00
10:30
11:00

bookings 保存一次预约的整体信息：用户、资源、完整起止时间、状态和幂等键。booking_slots 保存具体被占用的半小时时段，并通过 booking_id 关联到这笔预约。

这样设计后，查询可用时段时可以直接判断某个半小时起点是否已经被占用，也可以用数据库约束阻止同一资源的同一时段被重复写入。

二、事务保证一次预约整体成功#

BookingService.create() 使用 @Transactional：

开启事务
  → 保存 Booking
  → 保存全部 BookingSlot
  → flush
  → 方法正常返回
  → 提交事务

一次预约可能包含多条 SQL。单条 SQL 执行成功，不代表整个事务已经提交。假如预约记录和第一个时段已经写入，第二个时段发生冲突，异常会使整个事务回滚，之前写入的预约和时段也会被撤销。

这保证了系统不会留下“预约记录存在，但只有部分时段被占用”的不完整数据。事务的核心要求是：一次业务操作中的相关写入要么全部成功，要么全部撤销。

三、数据库唯一约束是并发预约的最后防线#

booking_slots 表中有约束：

UNIQUE (resource_id, slot_start)

resource_id 是被预约资源的 ID，例如会议室或设备；slot_start 是半小时时段的起始时间。两列的组合不能重复：

resource_id slot_start 结果
1 2026-10-23 10:00 第一次插入成功
1 2026-10-23 10:30 成功，这是另一个时段
2 2026-10-23 10:00 成功，这是另一个资源
1 2026-10-23 10:00 失败，组合重复

查询可用时段只能说明“查询当时看起来空闲”。查询完成和真正插入之间存在时间间隔，多个请求可能同时查到空闲。因此，数据库写入时的唯一约束才是最终裁决。

四、并发请求如何被处理#

假设 20 个请求同时预约资源 1 的 10:00—10:30，并且每个请求使用不同的幂等键：

请求 A 查询：空闲
请求 B 查询：空闲
请求 C 查询：空闲
        ↓
多个事务尝试插入同一个 (resource_id, slot_start)
        ↓
数据库唯一约束裁决
        ↓
一个事务成功，其他事务失败并回滚

项目的并发测试使用 20 个线程和 CountDownLatch，先让所有线程准备好，再同时放行。测试最终验证：

assertThat(successes).hasValue(1);
assertThat(bookings.count()).isEqualTo(1);

这说明只有一个请求成功，而且失败请求创建的 Booking 也没有残留。失败请求通常返回 409 Conflict，表示请求与已经成功占用的时段发生冲突。

这也是为什么 Redis 不能替代数据库唯一约束。Redis 可以缓存可用时段，也可以作为辅助锁减少同时进入临界区的请求，但锁可能过期、应用可能崩溃、网络可能中断。真正阻止重复占用的仍然是数据库约束。

五、Redis 锁的作用#

Redis 锁是一种分布式互斥锁，用来让多个线程或多个应用实例尽量不要同时执行同一段关键代码。常见形式是：

SET lock:resource:1:10:00 request-id NX PX 10000

NX 表示只有 key 不存在时才创建，PX 设置自动过期时间，request-id 用来确认释放锁时确实是当前请求持有的锁。

Redis 锁适合减少重复计算、协调定时任务或降低数据库竞争。预约系统即使使用 Redis 锁，也必须保留 PostgreSQL 的唯一约束，因为 Redis 锁失效后不能阻止两个请求同时写入数据库。

六、幂等键解决重复请求#

并发和幂等解决的是不同问题。并发关注多个请求同时争抢同一时段；幂等关注同一个请求因为超时或重试被重复发送。

例如客户端第一次发送预约后没有收到响应，客户端可以使用同一个 Idempotency-Key 重试：

第一次：phase2-booking-001，资源 1，10:00—10:30
重试：  phase2-booking-001，资源 1，10:00—10:30

项目通过 (user_id, idempotency_key) 唯一约束限制同一个用户重复使用幂等键。Service 先按用户和幂等键查询已有预约：

  • 相同 key、相同资源和时间：返回原预约；
  • 相同 key、不同资源或时间：返回 409 Conflict；
  • 新操作使用新 key：按新的预约处理。

所以，幂等键不是预约 ID，也不是资源 ID。它是客户端为“一次业务操作”生成的标识，同一次操作重试时复用，发起新操作时更换。

七、三个约束分别解决什么问题#

事务
  保证一笔预约的多条写入整体成功或整体回滚

唯一约束 (resource_id, slot_start)
  防止并发请求重复占用同一个资源时段

唯一约束 (user_id, idempotency_key)
  防止同一个用户重复创建同一业务请求

它们不能互相替代。事务解决完整性，时段唯一约束解决资源竞争，幂等键解决网络重试。
